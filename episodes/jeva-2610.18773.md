## Introduction

Jeva is a new decision-making model designed to handle structured choices more effectively than current approaches. While existing models like Jev can make quick decisions, they often ignore key aspects of how decisions are actually made. Jeva addresses four important structural needs: it tells the difference between having no answer and being unsure, it makes decisions that don't change when options are reordered, it can handle growing lists of choices without needing new output formats, and it reuses computations across different requests to save time. This model uses a shared encoder to represent both the question and each option, and a decision stack that focuses only on the question while keeping the options fixed. These features allow Jeva to handle a wide range of choices, detect when there's no answer, and make decisions quickly without changing results when options are rearranged.

## Contributions

System one models make quick decisions like choosing a tool or assigning a score. These decisions need to follow rules: the choice shouldn't change if the options are reordered, the model must know when no option is correct, and it should handle any number of options without needing new output formats. Existing models like Jev often combine the way they process the question and the options, which makes it hard to reuse computations across different requests and can let the order of options affect the decision. This limits how well they handle large sets of options and makes it harder to tell if no option is correct.

Existing models can't tell the difference between having no answer and being unsure about the options. Most models use a fixed set of answer symbols and normalize scores over the given options, which doesn't clearly separate when no option is valid from when the model is just unsure. Jeva adds a coverage gate that separates the probability of having no answer from the probability of choosing any of the options, making it clear when no option applies.

Models often change their decision when the order of options changes, which is not ideal for structured choices. Many models treat the set of options as an ordered sequence, which means the position of an option can accidentally influence the decision. Jeva uses permutation-equivariant probabilities, so the decision remains the same no matter how the options are ordered.

Handling large numbers of options is inefficient and requires new output formats in existing models. Current models normalize scores over the given options, which doesn't scale well with large candidate sets and limits the number of options they can handle. Jeva uses a decision mixer that allows it to handle up to two thousand and forty eight options without expanding the output parameters, making it much faster than other models.

Existing models can't reuse computations across different requests, which makes them slower for new tasks. Most models process the request and options together, so changing the request or recombining options requires reprocessing the entire context. Jeva separates the encoding of the request from the options, allowing the model to cache the representations of the options and reuse them across different requests, which cuts down the time needed for new tasks by over twenty times.

## The shared encoder

Here is how it works. The method has five pieces: the shared encoder, the decision stack, the coverage gate, the cache system and the training loss.

The shared encoder takes the question, decision type, and each option and turns them into compact vectors. These vectors let the model reuse computations across different requests. First, it formats the request with a template that combines the decision type, question, and state. Each option gets a simpler template with just the decision type and its text. Then, both formatted texts go through a language model to get their representations. The model pools the last nonpadding token from each text. Next, it applies bias-free projections to these pooled vectors. Finally, it normalizes the option vectors using stabilized ℓ₂ normalization. This gives a request vector and a set of option vectors. The option vectors are fixed during a forward pass, but the encoder and projections stay trainable. The request vector is refined later, while the options stay the same. This setup lets the model reuse option vectors across different requests, making decisions faster and more efficient. The normalization ensures stable representations, and the separate templates help the model understand each input's role.

## The decision stack

The decision stack takes the initial request vector and processes it through a series of blocks to refine its understanding of the options. Each block uses multi-head attention over the fixed option vectors, keeping them unchanged while the request state evolves.

For each of the L blocks, the option vectors are processed through H attention heads. Each head starts by creating a query vector from the current request state using a normalized linear projection. Then, for each option, key and value vectors are computed from the option vectors using similar projections.

The compatibility between the query and each key is calculated as their dot product. These scores are then scaled by a temperature parameter and passed through a softmax to create attention weights. These weights ensure that the model spreads its focus across options in a way that keeps the decision stable even if the options are reordered.

The weighted values from all options are summed and combined across heads. This result is transformed through an output projection to create a message specific to the block. The request state is then updated using two steps: first, the message is added to the current state, and then a SwiGLU network is applied after a normalization step.

Only the request state changes through these blocks, while the option vectors stay fixed. This process lets the model focus on the request while maintaining the structure of the options, making decisions more stable and scalable.

## The coverage gate

The coverage gate estimates the chance that at least one valid option exists and separates this from the chance of choosing any specific option. It starts with the final request state and each option's vector, taking their dot product to get a score for every option. These scores are then softened using a temperature parameter, turning them into probabilities that show how likely each option is, given the request.

Next, it finds the highest score among all options. This maximum score is used with a learned threshold and another temperature to calculate the coverage probability. This probability tells how likely it is that at least one option is valid. The chance of no valid option is just one minus this coverage probability.

The final step scales the option probabilities by the coverage probability, ensuring that no option is chosen if none are valid. This creates a full probability distribution that includes both the chance of choosing an option and the chance of having no valid choice. The coverage gate makes it clear when no option is correct, unlike other models that mix these possibilities. It uses two learned temperatures to control how sensitive the scores are to differences and how confident the model is about coverage.

## The cache system

The cache system stores precomputed semantic vectors and projected views for each option in a memory bank. It also caches assembled candidate tuples so they can be reused across different requests. When a new request comes in, it can pull these stored representations instead of recomputing them, saving time. The system keeps the order of options separate from the final decision, so changing the order doesn’t affect the outcome. It uses two types of caching: one for individual options and another for groups of options that have been combined before. This lets the model handle large numbers of choices without needing new output formats. The cache ensures that even if the same option appears in different requests, its representation is reused, cutting down on computation. The system also keeps the decision process focused on the request itself, not the order of the options. This makes the model faster and more efficient for repeated or similar tasks.

## The training loss

The training loss combines two parts to guide the model. First, it uses a binary cross-entropy between the coverage estimate and a target that tells if any option is valid. This helps the model learn when no answer exists. Second, it subtracts the sum of each candidate's label multiplied by the log of its probability. This part ensures the model picks the right option when one exists. These two parts are added together to form a single loss that trains both null detection and typed decisions at the same time. The model uses a specific optimization setup: rank-sixty-four LoRA with separate AdamW groups and global gradient clipping to keep training stable. It also follows a curriculum that starts with simpler decisions and moves to more complex ones, like verification and handling large sets of options. This training method helps the model learn efficiently and adapt to different tasks. The final model has parameters that make decisions quickly and reuse cached option data, making it fast for new requests.
